片方の端末がBluetooth Low Energy（BLE）で書き込んだ値は、もう片方のアプリにどう届くのか。OpenCI v2.6.0では、送信側と受信側を同じCIジョブで検証できます。サンプルでは、1台のMacで2台のiOSシミュレーターを起動し、仮想のBluetooth接続を使ってFlutterアプリ同士で通信します。

## ひとつの値を、送信から返信まで追う

ワークフローはPatrolのテストを一度ビルドし、両方のシミュレーターにインストールします。まずBが、読み取り可能なGATTキャラクタリスティックを公開します。Aはそこから値を読み取り、続いて実行ごとに生成した16バイトを書き込みます。Bが受け取った値を画面に表示してAに送り返し、両方のアプリが記録した値が一致すればテストは成功です。

試すには、Flutter 3.47.8、Python 3.13、Xcode、iOSシミュレーターのランタイムを用意したMacで、v2.6.0のタグをチェックアウトします。リポジトリのルートで次のコマンドを実行してください。

```sh
flutter pub get
dart run openci/virtual_ble_ci.dart
```

自分のPatrolテストでも `openCI.patrol.testWithVirtualBle()` を使えます。戻り値のディレクトリには、端末ごとのログとXCTestの結果が残ります。サンプルでは両方のアプリからJSONも回収し、送った値と受け取った値を照合しています。[Flutterサンプル](https://github.com/openci-org/openci/tree/v2.6.0/packages/openci_virtual_ble) · [ワークフローSDK 0.5.3](https://pub.dev/packages/openci_workflow/versions/0.5.3)

## PRからエラーの行を開く

PRのワークフローが失敗またはタイムアウトすると、OpenCIはそのPRに原因の要約をコメントできます。たとえばDartの解析エラーなら、行番号をクリックすると、CIがテストしたコミットの該当行が開きます。続けて失敗したときは同じコメントが更新され、成功すると解決済みになり、以前のエラーは折りたたまれます。対象のmacOSジョブは、終了後にダッシュボードのジョブ詳細から再実行できます。[コメントの実例](https://github.com/openci-org/openci/pull/4010#issuecomment-7009043736) · [ジョブの再実行](https://github.com/openci-org/openci/pull/3959)

## GitHub Releaseの公開をきっかけにデプロイする

今週先に公開したv2.5.1で、GitHub Releaseをきっかけにワークフローを実行できるようになりました。`CITrigger.release(tag: 'v*')` を指定すると、該当するリリースの公開時に、そのタグのコミットにあるワークフローが動きます。さらに、pub.devで公開済みの `openci_workflow` 0.5.3には `openCI.firebase.functions.deploy()` が加わりました。インストール済みのFirebase CLIを使って、指定したプロジェクトへデプロイします。コードベース名を渡せば、そのコードベースだけをデプロイできます。[リリーストリガー](https://github.com/openci-org/openci/pull/3993) · [Firebase Functionsの使用例](https://github.com/openci-org/openci/blob/v2.6.0/packages/openci_workflow/README.md#firebase-functions)

Webダッシュボードでは、Cloudチームのビルド一覧の上に当月のCI利用額の見込みを表示します。金額を選ぶと、そのチームの請求詳細を開けます。[月ごとのCI利用額](https://github.com/openci-org/openci/pull/3989)
