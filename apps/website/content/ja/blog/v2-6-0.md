片方の端末がBluetooth Low Energy（BLE）で書き込んだ値は、もう片方のアプリにどう届くのか。OpenCI v2.6.0では、送信側と受信側を同じCIジョブで検証できます。サンプルでは、1台のMacで2台のiOSシミュレーターを起動し、仮想のBluetooth接続を使ってFlutterアプリ同士で通信します。

前回の週次版は11月13日のv2.5.0です。19日のv2.5.1では、PRのジョブを再実行できるようになり、GitHub Releaseからモバイルアプリをテスターに届けるところまで自動化しました。20日のv2.6.0には、2台でのBLEテスト、PR上のエラー表示、Firebase FunctionsのデプロイAPIが入りました。ダッシュボードのログインテストも、SDKの公開前テストも、OpenCI上で動いています。

## ひとつの値を、送信から返信まで追う

ワークフローはPatrolのテストを一度ビルドし、両方のシミュレーターにインストールします。まずBが、読み取り可能なGATTキャラクタリスティックを公開します。Aはそこから値を読み取り、続いて実行ごとに生成した16バイトを書き込みます。Bが受け取った値を画面に表示してAに送り返し、両方のアプリが記録した値が一致すればテストは成功です。

試すには、Flutter 3.47.8、Python 3.13、Xcode、iOSシミュレーターのランタイムを用意したMacで、v2.6.0のタグをチェックアウトします。リポジトリのルートで次のコマンドを実行してください。

```sh
flutter pub get
dart run openci/virtual_ble_ci.dart
```

自分のPatrolテストでも `openCI.patrol.testWithVirtualBle()` を使えます。戻り値のディレクトリには、端末ごとのログとXCTestの結果が残ります。サンプルでは両方のアプリからJSONも回収し、送った値と受け取った値を照合しています。[Flutterサンプル](https://github.com/openci-org/openci/tree/v2.6.0/packages/openci_virtual_ble) · [ワークフローSDK 0.5.3](https://pub.dev/packages/openci_workflow/versions/0.5.3)

初期のテストが失敗したとき、2台のログを並べると、AのDartテストが起動するのとほぼ同時にBが4分の待ち時間を使い切っていたことが分かりました。そこでBの待ち時間を9分に延ばし、Aの起動を意図的に250秒遅らせても往復が成功することを確かめました。OpenCI上でも2台のiPhone 17 Proシミュレーターで、同じ16バイトをBが受信し、Aが受け取り直した記録を確認できます。[テスト結果と端末ごとのログ](https://github.com/openci-org/openci/pull/4007)

## iOSアプリの起動からサインインまでをテストする

ダッシュボードのiOSテストは、毎回新しいシミュレーターから始まります。Patrolがログイン画面を開き、ホーム画面に戻ってからアプリを開き直し、既存のテストアカウントでサインインします。成功条件は、Firebase Authenticationで認証し、所属チームを読み込んでダッシュボード本体が表示されることです。[実際に通ったiOSテスト](https://github.com/openci-org/openci/runs/134751813207)

自分のアプリで同じ流れを組むには、`launchIosSimulator()` で起動完了を待ち、返ってきた `id` を `patrol.test()` の `device` に渡します。テスト用の認証情報は `env` にOpenCIのシークレットを指定し、テスト側で `const String.fromEnvironment(...)` を使って元のキー名で読み取れます。`finally` で `simulator.dispose()` を呼ぶと、途中でテストが失敗しても端末を削除できます。[ダッシュボードのワークフロー](https://github.com/openci-org/openci/blob/v2.6.0/openci/dashboard_ios_patrol_ci.dart)

## PRからエラーの行を開き、ジョブを再実行する

PRのワークフローが失敗またはタイムアウトすると、OpenCIは失敗したステップの要約をそのPRに投稿できます。たとえばDartの解析エラーなら、行番号をクリックして対象のPRコミットのファイルを開けます。同じワークフローが続けて失敗すると同じコメントが更新され、成功すると解決済みになり、以前のエラーは折りたたまれます。[コメントの実例](https://github.com/openci-org/openci/pull/4010#issuecomment-7009043736)

ベースブランチがレビュー中に進むと、GitHubが用意したテスト用マージコミットが古くなることもあります。OpenCIはベースとPRの先端を再確認し、GitHubのマージ結果が最新ならそれを使います。準備が間に合わない場合は、確認済みの2つのコミットをビルド用VM内でマージします。コンフリクトがあればチェックアウトで止まり、成功時は実際にテストしたマージコミットがログに残ります。PRのマージ先を変更した直後にforce-pushした場合も、古い通知が最新のビルド計画を中断しないようにしました。[PRのチェックアウト処理](https://github.com/openci-org/openci/pull/3962) · [古いPR通知の扱い](https://github.com/openci-org/openci/pull/3992)

一時的な失敗をもう一度試すには、ダッシュボードのジョブ詳細で「再実行」を押してください。終了済みのmacOSジョブが対象で、ジョブに保存されたリビジョンと過去のログを引き継ぎます。待機中は前回のログを読めて、新しい実行が始まると表示が切り替わります。再実行には新しいGitHub Checkも付きます。[再実行の操作とログ](https://github.com/openci-org/openci/pull/3959) · [同じリビジョンで再実行した例](https://github.com/openci-org/openci/pull/3957)

## Webプレビューの有効期限をPRに載せる

この公式サイトのPRを開くと、レビュー用のURLとQRコードが届きます。ワークフローは `openCI.context` からPR番号を取得して、同じPRの更新には同じFirebase Hostingチャネルを使います。プレビューの有効期間はこのサイトでは7日間。更新すると期限が延び、コメントにもFirebaseが返した実際の有効期限がUTCで表示されます。[このサイトの公開ワークフロー](https://github.com/openci-org/openci/blob/v2.6.0/openci/website_ci.dart)

SDK 0.4.0から、`deployPreview()` の戻り値にはURLと有効期限の両方が入ります。以前は戻り値をURLとしてそのまま渡していた箇所を、次の形に変更できます。

```dart
await openCI.pullRequest.postQrCode(
  url: preview.url,
  expiresAt: preview.expiresAt,
);
```

コメントを日本語にするには `lang: PostQrCodeLang.ja` を渡します。プレビューと本番の両方に `firebaseConfigPath: 'firebase.json'` を指定すると、公開ディレクトリ、除外パターン、静的なルーティング、レスポンスヘッダーを同じ設定から読み込めます。[Hosting設定の読み込み](https://github.com/openci-org/openci/pull/3936) · [プレビューAPIの移行例](https://github.com/openci-org/openci/pull/3940)

## Dartのコード生成、解析、テストをワークフローに書く

コード生成を使うパッケージでは、生成を済ませてから解析し、影響のあるテストだけを選んで実行できます。次はリポジトリのルートから、SDKパッケージを対象に実行する例です。

```dart
const pkg = 'packages/openci_workflow';
await openCI.dart.runBuildRunner(dir: pkg);
await openCI.dart.analyze(dir: pkg, fatalInfos: true);
await openCI.dart.test(dir: pkg, paths: ['test/src/dart/dart_ci_test.dart']);
```

`paths` を省略すればパッケージのテスト一式が走ります。Flutter側では `OpenCI.init` の `flutterVersion` に `FlutterVersion.v3_44_8.value` または `FlutterVersion.v3_47_8.value` を指定できます。BLEサンプルのCIでは `flutter.pubGet(enforceLockfile: true)` でロックファイルどおりに依存関係を取得し、続く静的解析には `noPub: true` を渡しています。[ワークフローガイド](/ja/docs/workflows/) · [BLEサンプルの検証コード](https://github.com/openci-org/openci/blob/v2.6.0/openci/lib/virtual_ble_checks.dart)

SDK自身のpub.dev公開もOpenCIで実行します。`develop` でパッケージの `pubspec.yaml` または `CHANGELOG.md` が変わると、2台のシミュレーターでBLEの往復を検証してから `dart.publishToPubDev()` を呼びます。`skipIfPublished: true` を指定しているので、同じバージョンでジョブを再実行したときはアップロードをスキップします。[SDKの公開ワークフロー](https://github.com/openci-org/openci/blob/v2.6.0/openci/openci_workflow_cd.dart)

## GitHub Releaseでアプリを配布し、Functionsをデプロイする

v2.5.1で加わった `CITrigger.release(tag: 'v*')` は、名前が一致するGitHub Releaseを公開したときに動きます。公開したプレリリースも対象で、ワークフローはタグのコミットから読み取ります。SDK 0.5.0より前から `CITrigger` を網羅的に `switch` している場合は、`release` の分岐を追加してください。[リリーストリガー](https://github.com/openci-org/openci/pull/3993)

ダッシュボードでは、このトリガーでShorebirdのリリースビルドを作ります。11月19日のアプリ版2.5.1では、iOSビルド `16342` がTestFlightの内部テスターへ、Androidビルド `16341` がGoogle Playの内部テストトラックへ届きました。その後の変更は、`develop` へのマージを起点に各プラットフォームの最新リリースへ `stable` パッチを作成します。共通のDartコードが変われば両方が、iOS固有のコードが変わればiOS側のジョブが動きます。[ストア向けビルド](https://github.com/openci-org/openci/pull/3996) · [内部配布したビルドとパッチの条件](https://github.com/openci-org/openci/pull/3995)

バックエンドでは、OpenCIのTypeScript製Firebase FunctionsとDart製のワークフロープランナーも同じリリースタグからテストします。本番へのデプロイ直前に、そのタグがまだ最新の安定版かを再確認します。自分のプロジェクトでは、pub.devで公開済みのSDK 0.5.3に入った `openCI.firebase.functions.deploy()` が使えます。実行環境のFirebase CLIで、プロジェクトIDと、必要なら対象コードベースを指定してデプロイできます。[OpenCI本体のデプロイ](https://github.com/openci-org/openci/pull/4008) · [Functions APIの使用例](https://github.com/openci-org/openci/blob/v2.6.0/packages/openci_workflow/README.md#firebase-functions)

## チームを作り、リポジトリを接続する

ダッシュボードの新規登録は「Google で続行」から始めます。初回セットアップが中断しても、次のサインインで所属チームを調べて再開します。既存のメール・パスワードアカウントでは従来の方法でサインインでき、設定の「チーム作成」から別のチームも追加できます。[登録と初回セットアップ](https://github.com/openci-org/openci/pull/3969) · [チームの追加](https://github.com/openci-org/openci/pull/3924)

GitHub Appをインストール済みなら、リポジトリのWrite、Maintain、Admin権限を持つメンバーが、そのリポジトリをOpenCIチームに接続できます。一つのOrganizationにアプリをインストールして、リポジトリごとに別々のOpenCIチームへ割り当てることもできます。[リポジトリ単位の接続](https://github.com/openci-org/openci/pull/3950)

稼働後は、Webダッシュボードのビルド一覧の上で、選択中のCloudチームの当月のCI利用額を税込みの円で確認できます。その場で見込額を更新したり、金額を選んで同じチームの請求詳細を開いたりできます。[月ごとのCI利用額](https://github.com/openci-org/openci/pull/3989)

## macOSワーカーで何を実行するか

OpenCIリポジトリでは、ワークフロースクリプトの解析とテストを独立したジョブにしました。生成されたワークフローファイルだけを更新したPRなら、macOSアプリのリリースビルドを待たずにレビューできます。ダッシュボード本体や直接依存するパッケージが変わったときは、macOS側のチェックも走ります。[ワークフローのテストとmacOSビルドの実行条件](https://github.com/openci-org/openci/pull/3965)

ビルド用VMの標準CPU数は4になりました。また、macOSベースイメージv0.1.9にはPatrol CLI 4.9.0が入っています。シミュレーターを使うジョブでは、あらかじめ用意したCLIでテストを始められます。[ワーカーのCPU割り当て](https://github.com/openci-org/openci/pull/3978) · [Patrolを含むmacOSイメージ](https://github.com/openci-org/openci/pull/3958)
