We bought a Linux machine this week.

## Running Android E2E tests for a few yen

It feels like more mobile teams want to run end-to-end (E2E) tests on every change. On a paid macOS runner, a single run can cost hundreds of yen, and a long one can run into the thousands. At those prices, I’d think twice before rerunning a test for a small fix.

OpenCI’s macOS runner costs ¥1 per minute under yen billing. GitHub Actions lists its standard macOS runner at $0.062 per minute. At an illustrative ¥150 to the dollar, OpenCI’s per-minute rate is about a tenth of that. A 30-minute test costs ¥30 on OpenCI, but that still adds up when you run several scenarios on every pull request. [GitHub Actions runner pricing](https://docs.github.com/en/billing/reference/actions-runner-pricing)

With Flutter, your iOS and Android apps share code. You can keep testing iOS-specific behavior on iOS and run common scenarios, such as signing in or moving between screens, on an Android emulator on Linux. That’s why we added a Linux worker to OpenCI.

The machine we bought has 8 CPU cores, 16 threads, and 32 GB of RAM. In workflow SDK 0.9.0, you can select Linux Large to get **4 vCPUs and 8 GiB of RAM for ¥0.1 per minute, tax included.** A 30-minute E2E run costs ¥3. For comparison, GitHub Actions lists its paid 4-core x64 Linux runner at $0.012 per minute, or ¥1.8 at the same exchange rate. [OpenCI’s yen pricing (Japanese)](/ja/pricing/) · [Linux Large](https://github.com/openci-org/openci/pull/4073)

I’d like you to be able to rerun a test whenever it helps you make a better app, without worrying about what your PM or CEO will think of the bill.

We’re piloting the Linux workers with selected repositories, and we can only run so many jobs at once. If you find yourself waiting in the queue, please tell us. We’ll add machines and memory as usage grows.

## Read CI logs directly from Codex or Claude

We also added an MCP server to the OpenCI CLI. When we asked Codex or Claude to investigate a CI failure, we used to have it open the dashboard with Computer Use and click through to the right job.

Once you’ve connected the MCP server, paste the pull request URL and ask, “Which step failed? Show me the logs around the error.” The assistant can read the relevant lines directly. We expect that to shorten the time it takes to find the cause and save the tokens we used to spend reading the screen. [CLI setup guide](/en/docs/cli/)

We also added `retryBuildJob()` to the CLI’s API client. It lets you request another run of a finished job through the API. [Job retry API](https://github.com/openci-org/openci/pull/4039)

## What else changed this week

- With `pathsIgnore`, you can skip CI when every file changed in a pull request or push matches an excluded path, for example when a PR only updates the README.
- You can now keep Android and iOS workflows in separate subdirectories under `openci/`.
- When two GitHub pull requests share a commit, each shows the test result for its own merge target. Select **Details** to open the log for that job.
- One **Shorebird** release now produces both an APK and an AAB. Firebase App Distribution also accepts individual testers’ email addresses and tester groups.
- A **TestFlight** workflow can now create a standard encryption declaration and apply it to a build after Apple approves it.
- You can build a **Flutter Web** release with `ci.flutter.buildWeb()`. We use it to build the OpenCI Dashboard.
- The new homepage has an interactive demo of Flutter PR checks and app distribution. We also made a page to thank the people who contribute machines and infrastructure. [Workflow demo](/en/) · [Special Thanks](/en/thanks/)

We’re building OpenCI to be a genuine CI/CD service for Flutter developers. If there’s a feature you’d like or something you find awkward, we’d love to hear from you. We’ll also help you set up CI/CD for free, whatever the size of your project. [Book a free setup call](https://cal.com/masahiro-aoki-r4rxdx/15min)
