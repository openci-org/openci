What does the second phone actually receive when the first one writes a value over Bluetooth Low Energy (BLE)? In OpenCI v2.6.0 you can check both ends of that exchange in CI. The Flutter example runs on two iOS simulators on the same Mac and uses a virtual Bluetooth connection.

Two releases landed after the November 13 weekly release, v2.5.0. The November 19 patch, v2.5.1, put a retry button on finished jobs and wired GitHub Releases to mobile test distribution. November 20’s v2.6.0 added the two-device BLE test, failure comments on pull requests and a Firebase Functions deployment API. Both the dashboard’s sign-in test and the SDK’s pre-publication checks now run on OpenCI.

## Follow one value across two screens

The workflow builds the Patrol test once and installs it on both simulators. Simulator B first publishes a readable GATT characteristic. Simulator A reads it, then writes a fresh 16-byte value. B displays the value and sends it back. The test passes when the bytes recorded by both apps match.

To try it, check out the v2.6.0 tag on a Mac with Flutter 3.47.8, Python 3.13, Xcode and an iOS Simulator runtime. Run these commands from the repository root.

```sh
flutter pub get
dart run openci/virtual_ble_ci.dart
```

To use the same setup in your own Patrol test, call `openCI.patrol.testWithVirtualBle()`. It returns a directory with each simulator’s log and XCTest result bundle. The example also asks both apps for a JSON file so the workflow can compare what each peer received. [Flutter example](https://github.com/openci-org/openci/tree/v2.6.0/packages/openci_virtual_ble) · [Workflow SDK 0.5.3](https://pub.dev/packages/openci_workflow/versions/0.5.3)

Those two logs helped diagnose an early failure. Simulator B waited four minutes for its peer and timed out just as A’s Dart test was starting. We extended B’s wait to nine minutes, then deliberately delayed A’s launch by 250 seconds and saw the round trip complete. A run on two iPhone 17 Pro simulators also recorded the same 16 bytes arriving at B and coming back to A. [Test results and per-device evidence](https://github.com/openci-org/openci/pull/4007)

## Take an iOS app from launch through sign-in

The dashboard’s iOS test starts with a fresh simulator. Patrol opens the sign-in screen, returns to the home screen, reopens the app, then signs in with an existing test account. To pass, the app has to authenticate with Firebase, load the user’s team and display the dashboard. The CI run records the result of that whole interaction. [Passing dashboard sign-in test](https://github.com/openci-org/openci/runs/134751813207)

For a similar test in your own app, `launchIosSimulator()` waits for the new device to boot. Pass its `id` to the `device` argument of `patrol.test()`. The `env` argument accepts OpenCI secrets for the test account. Test code reads them under their original keys with `const String.fromEnvironment(...)`. Calling `simulator.dispose()` in a `finally` block removes the device even if a test fails. [Dashboard Patrol workflow](https://github.com/openci-org/openci/blob/v2.6.0/openci/dashboard_ios_patrol_ci.dart)

## Find the failing line and retry the job

When a PR workflow fails or times out, OpenCI can post a summary of the failed step in the conversation. For a recognized Dart diagnostic, click the line number to open the file at the reported PR commit. A repeat failure updates the same comment. Once the workflow passes, the comment marks it resolved and folds away the previous errors. [Example failure comment](https://github.com/openci-org/openci/pull/4010#issuecomment-7009043736)

A moving base branch can leave GitHub’s test merge commit out of date. OpenCI rechecks the base and PR head and uses GitHub’s merge if it is current. If GitHub is still preparing the merge, the build VM creates it from those two verified commits. A conflict stops the checkout. A successful checkout records the exact merge commit in the log. We also fixed a race when a PR is retargeted and then force-pushed. The older notification can now finish without interrupting the plan for the newer revision. [PR checkout changes](https://github.com/openci-org/openci/pull/3962) · [Handling stale PR notifications](https://github.com/openci-org/openci/pull/3992)

For a transient failure, open the job details in the dashboard and choose **Retry job**. A finished macOS job keeps its saved revision and previous logs. You can read the previous attempt while the retry is queued. When the new run starts, the view follows its logs and GitHub gets a new Check. [Dashboard retry action](https://github.com/openci-org/openci/pull/3959) · [A retry on the same revision](https://github.com/openci-org/openci/pull/3957)

## Put the web preview’s expiry on the pull request

Open a PR against this website and the preview comment gives you a URL and QR code. The workflow reads the PR number from `openCI.context` and reuses the same Firebase Hosting channel on each update. This site requests a seven-day preview. A new deployment refreshes that deadline, and the comment shows the actual expiry returned by Firebase in UTC. [Website deployment workflow](https://github.com/openci-org/openci/blob/v2.6.0/openci/website_ci.dart)

Since SDK 0.4.0, `deployPreview()` returns both the URL and its expiry. If your workflow passed the return value directly as a URL, update the comment call to use the two fields.

```dart
await openCI.pullRequest.postQrCode(
  url: preview.url,
  expiresAt: preview.expiresAt,
);
```

Pass `lang: PostQrCodeLang.ja` for a comment in Japanese. Passing `firebaseConfigPath: 'firebase.json'` to both the preview and live deploys lets them share a public directory, ignore patterns, static routing and response headers. [Hosting configuration](https://github.com/openci-org/openci/pull/3936) · [Preview API migration](https://github.com/openci-org/openci/pull/3940)

## Generate code, analyze it and test a Dart package

A package that uses code generation can now generate its sources before analysis, then run just the tests for the change under review. This example starts at the repository root and targets the workflow SDK package.

```dart
const pkg = 'packages/openci_workflow';
await openCI.dart.runBuildRunner(dir: pkg);
await openCI.dart.analyze(dir: pkg, fatalInfos: true);
await openCI.dart.test(dir: pkg, paths: ['test/src/dart/dart_ci_test.dart']);
```

Omit `paths` to run the full package test suite. For Flutter jobs, `OpenCI.init` accepts `FlutterVersion.v3_44_8.value` or `FlutterVersion.v3_47_8.value` as its `flutterVersion`. The BLE example uses `flutter.pubGet(enforceLockfile: true)` to install the locked dependencies, then passes `noPub: true` to static analysis to keep that resolution for the check. [Workflow guide](/en/docs/workflows/) · [Checks used by the BLE example](https://github.com/openci-org/openci/blob/v2.6.0/openci/lib/virtual_ble_checks.dart)

The SDK also publishes itself through OpenCI. When its `pubspec.yaml` or `CHANGELOG.md` changes on `develop`, the publication job runs the two-simulator round trip before calling `dart.publishToPubDev()`. With `skipIfPublished: true`, retrying the same version skips the upload if pub.dev already has it. [SDK publication workflow](https://github.com/openci-org/openci/blob/v2.6.0/openci/openci_workflow_cd.dart)

## Ship mobile builds and Firebase Functions from a release

The `CITrigger.release(tag: 'v*')` trigger added in v2.5.1 runs when you publish a GitHub Release with a matching tag. Published prereleases also qualify. OpenCI reads the workflow at the tagged commit. If you are upgrading from before SDK 0.5.0 and have an exhaustive `switch` on `CITrigger`, add the new `release` case. [GitHub Release triggers](https://github.com/openci-org/openci/pull/3993)

The dashboard uses this trigger to create Shorebird release builds. For the November 19 dashboard release, version 2.5.1, iOS build `16342` reached internal testers on TestFlight and Android build `16341` reached the Google Play internal track. Merges to `develop` can then create a `stable` patch against the latest release on each platform. A change to shared Dart code selects both patch jobs. An iOS-only change selects the iOS job. [Store build workflows](https://github.com/openci-org/openci/pull/3996) · [Distributed builds and patch rules](https://github.com/openci-org/openci/pull/3995)

On the backend, OpenCI tests its TypeScript Firebase Functions and its Dart workflow planner from the same release tag. Just before deploying to production, it checks that the tag is still the latest stable release. For your own project, the published 0.5.3 SDK adds `openCI.firebase.functions.deploy()`. It uses the installed Firebase CLI and takes a project ID and, if you want to deploy a single codebase, its name. [OpenCI’s production workflow](https://github.com/openci-org/openci/pull/4008) · [Functions API example](https://github.com/openci-org/openci/blob/v2.6.0/packages/openci_workflow/README.md#firebase-functions)

## Create a team and connect its repositories

New dashboard users start with **Continue with Google**. If initial setup is interrupted, the next sign-in checks team membership and resumes setup. Existing email/password accounts can still sign in as before, and existing users can add a team from **Settings → Team → Create team**. [Sign-up and setup recovery](https://github.com/openci-org/openci/pull/3969) · [Creating an additional team](https://github.com/openci-org/openci/pull/3924)

Once the GitHub App is installed, a member with Write, Maintain or Admin access to a repository can connect it to an OpenCI team. An organization can install the app once and assign individual repositories to different OpenCI teams. [Repository-level connections](https://github.com/openci-org/openci/pull/3950)

Once builds are running, the web dashboard shows the selected Cloud team’s estimated CI spend for the month above its build list. The figure is in yen and includes tax. Refresh it in place or select the amount to open that team’s billing details. [Monthly CI spend](https://github.com/openci-org/openci/pull/3989)

## Choose which changes need a macOS build

In the OpenCI repository, workflow scripts now have their own analysis and test job. A PR that changes only generated workflow files can be reviewed without waiting for a macOS application release build. Changes to the dashboard or its direct dependencies still select the macOS checks. [Workflow tests and macOS build selection](https://github.com/openci-org/openci/pull/3965)

Build VMs now receive four CPUs by default. The v0.1.9 macOS base image also ships with Patrol CLI 4.9.0, so simulator jobs have a test runner available when they start. [Worker CPU allocation](https://github.com/openci-org/openci/pull/3978) · [macOS image with Patrol](https://github.com/openci-org/openci/pull/3958)
